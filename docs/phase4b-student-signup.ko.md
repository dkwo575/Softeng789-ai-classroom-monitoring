## 보호자 대상과 승인 조건

- 새 가입 폼은 DOB, 학교, 주소, 학생 전화, 선택 연락 이메일과 보호자 이름·관계·이메일·전화를 받습니다.
- Pacific/Auckland 날짜 기준 18세 미만은 보호자가 필요합니다. 정확한 18번째 생일부터 성인으로
  처리하고 윤년 생일은 Java LocalDate.plusYears와 동일하게 계산합니다.
  이는 프로젝트의 처리 기준이며 일반적인 법적 동의 연령을 단정하는 기준이 아닙니다.
- `adultConfirmed`는 기존 성인 얼굴 등록 동의에만 사용하며 보호자 대상 판정에 재사용하지 않습니다.
- 보호자 이메일이 학생 로그인 이메일 또는 입력한 학생 연락 이메일과 같으면 거부합니다.
  대소문자·주변 공백을 무시합니다. 서로 다른 주소라고 실제 보호자임이 증명되지는 않습니다.
- 신규 자기 가입에 보호자가 포함되면 이메일 확인, 명시적 가입 허가,
  Admin의 독립적 관계 확인을 모두 완료해야 승인됩니다. 미완료 시 사유가 있는 HTTP 400을 반환합니다.
- 기존 학생, 직원이 만든 기록을 활성화하는 학생, 보호자가 없는 자기 가입은 기존 승인 계약을 유지합니다.
  이전 클라이언트의 profile 생략도 호환합니다. 새 UI의 DOB 필수 조건을 기존 계정에 소급하지 않습니다.
- 입력된 DOB가 미성년이면 성인 얼굴 등록 파일럿에 진입할 수 없습니다.
  미성년자 얼굴 등록을 허용하거나 모든 학생에게 얼굴 등록을 강제하는 변경은 포함하지 않습니다.
- 로그인 이메일은 기존 계정 계약에 따라 필수입니다. 선택 연락 이메일은 로그인 주소가 아니며
  보고서 발송에 사용하지 않습니다. 이메일 없는 학생과 보호자를 통한 비밀번호 복구는 후속 작업입니다.
- 기존 Student ID와 계정 이메일로 같은 계정에 로그인할 수 있고, 두 식별자는 같은 로그인 시도 제한을
  공유합니다. 보호자 이메일을 학생 로그인 식별자로 사용하지 않습니다.

보호자 기능 커밋은 기존 Student ID 입력 계약을 유지합니다. 자동 번호 발급은 별도 검토 가능한
변경으로 분리하며 기존 ID를 다시 매기지 않습니다.

## 사용자 흐름

1. 학생이 정보와 기존 출석 방식을 제출하면 계정·수강 요청은 PENDING입니다.
2. 대기 화면에서 프로필과 확인 상태를 보고, 저장 후 학생 또는 보호자 이메일 확인을 요청합니다.
3. 기존 메일 큐가 설정된 전송기를 사용합니다. 메일 미설정은 명확한 실패로 알리며
   디버그 링크나 가짜 성공 처리를 하지 않습니다. 불확실한 전송은 자동 재전송하지 않습니다.
4. 보호자는 메일 링크로 들어가 내용을 확인하고 가입 허가를 체크한 뒤 확인 버튼을 누릅니다.
5. Admin은 Registrations의 Guardian details에서 기존 확인된 입학 기록 또는 대면 확인을 근거로
   관계 확인을 기록합니다. 새 번호로 전화했다는 사실만으로 확인하지 않습니다.
6. 기존 가입 심사를 거쳐 계정·수강이 승인됩니다. 보호자 확인만으로 자동 승인되지 않습니다.

토큰은 URL fragment로 받고 기존 App이 주소창에서 제거합니다. POST 본문으로만 보내고 DB에는
해시만 저장합니다. 30분 만료·1회용이며 학생 UUID와 보호자 revision에 연결됩니다.
형제자매가 같은 보호자 이메일을 사용해도 인증은 학생별입니다.
대기 중 보호자 정보 변경은 기존 확인을 지우고 revision을 바꿔 이전 링크를 무효화합니다.
비밀번호·계정 상태 변경도 기존 링크의 유효성 검사에 반영합니다.

보호자 링크 확인 응답에는 학생 표시 이름과 링크 목적·역할만 포함하고
이메일·Student ID·수업·전화·주소·학생 UUID는 내보내지 않습니다.
링크를 열기만 해서는 동의가 기록되지 않습니다.
없는·만료된·사용된·누락된 토큰은 같은 오류를 반환합니다. 개인정보는 로그에 남기지 않습니다.

## 프로필과 권한

기존 학생 Profile에 SelfProfileEditor를 연결하고 ConsentPanel은 유지합니다.
새 구현은 public index를 가진 `features/student-signup/`에 있으며 직원용
`features/student-profile/`은 변경하지 않습니다.

학교·주소·전화·연락 이메일을 직접 수정할 수 있습니다.
DOB는 미입력 상태에서 보완할 수 있으며 이미 저장된 DOB·이름, 로그인 이메일,
승인된 보호자 정보 변경은 학교에 요청합니다. 이번 작업에 별도 관리자 신원 정정 화면은 없습니다.
대기 중 보호자 정보를 정정하면 다시 확인해야 하며 확인 대상 보호자를 스스로 제거할 수 없습니다.

프로필 저장은 허용된 필드와 마지막 조회 version만 받습니다.
동시 수정 시 409를 반환하고 초안을 유지하며 명시적으로 변경 취소·다시 불러오기가 가능합니다.
Student ID·로그인 식별자·승인·수강·계정 상태·동의는 이 API로 바꿀 수 없습니다.
대기 학생의 일반 포털 API 접근 제한과 TeacherScopeSupport는 유지합니다.

## API

| 경로 | 권한 / 처리 |
| --- | --- |
| GET /api/auth/signup/profile | 학생 본인, PENDING 포함 |
| PUT /api/auth/signup/profile | 학생 본인, version + 허용 필드 |
| POST /api/auth/signup/verification | 학생 본인, 학생/보호자 이메일 확인 요청 |
| POST /api/auth/account-links/inspect | 기존 공개 경로, CSRF 및 토큰 검사 |
| POST /api/auth/account-links/confirm-contact | 정확한 공개 POST, 토큰·가입 허가·안내 버전 |
| GET /api/students/{id}/signup-profile | Admin 전용 |
| POST /api/students/{id}/guardian-confirmation | Admin 전용, 최신 revision·확인 방법·명시적 확인 |

새 공개 경로는 confirm-contact 하나이며 와일드카드나 GET 쓰기 작업은 없습니다.
기존 fragment 처리로 동작하므로 App.tsx를 변경하지 않습니다.

## DB 및 검증

스키마 변경은 V11에만 모읍니다. 학생 컬럼·보호자 연결 테이블·account_links의 대상 바인딩을
추가하고 기존 계정 링크 목적 세 가지와 KIOSK 세션 제약을 유지합니다.
학생·출석·수강·결제 기록은 삭제하거나 다시 번호를 매기지 않습니다.
V1–V10, 역사적 schema.sql, 잠금 파일과 로컬 데이터는 변경하지 않습니다.

테스트는 보호자가 없는 가입·기존/직원 생성 계정의 승인 호환성, 보호자 별도 동의,
동일 이메일 거부, 형제자매 인증 분리, 변경된 정보의 토큰 무효화, 동시 수정,
HTTP 접근 경계·CSRF·동일 오류를 검증합니다. 프론트엔드는 날짜 경계·폼·API를 검증합니다.
H2 테스트는 PostgreSQL 마이그레이션 검증을 대신하지 않습니다.
실제 PostgreSQL 스키마 검증은 Docker가 있는 Ubuntu CI에서 실행해야 합니다.

Claude 통합 후 확인: 보호자 있음/없음 가입, 메일 전송과 링크, Admin 관계 확인,
대기 계정 접근 제한, Profile 저장·충돌, 기존 ConsentPanel, 데스크톱·390px.
실제 메일과 UI 검증은 단위 테스트 통과만으로 완료했다고 보지 않습니다.

## 알려진 한계: 동일인 중복 계정

이번 단계는 한 사람이 학생 계정을 여러 개 갖는 것을 완전히 막지 못합니다.
서버는 이미 등록된 Student ID나 로그인 이메일만 거부합니다(대소문자 무시).

- Student ID는 학생이 직접 입력하며 학교 기록과 대조하지 않습니다. 쓰이지 않은 ID와 다른
  이메일을 넣으면 새 대기 계정이 만들어집니다.
- 직원이 만든 기록은 학생이 그 Student ID를 정확히 입력하고 메일함을 인증해야 연결됩니다.
  다른 ID와 다른 이메일로 가입하면 두 번째 계정이 생깁니다.
- 이름·생년월일·보호자 정보가 같아도 가입을 막지 않으며, 얼굴 유사도로 거부하지도 않습니다.

계정 조정 기능이 생기기 전까지 Admin은 승인 전에 대기 가입을 기존 학생과 이름·생년월일·
보호자 정보로 대조하고, 중복이면 거절해야 합니다. 같은 이유로 Student ID 자동 발급은
보류했습니다. 제안은 커밋 `a6f7f45`로 보존하며, 기존 기록 연결·중복 처리·ID 형식을 정한 뒤
별도 마이그레이션으로 다시 추가합니다.

## 후속 범위

이메일 인증만으로 실제 보호자임을 증명하지 않습니다. Admin의 독립된 근거 확인이 필요합니다.
동명이인은 허용하며 얼굴 유사도로 중복 가입을 차단하지 않습니다.
ID/이메일 중복 방지를 넘어선 동일인 계정 조정, 보호자 포털, 이름·DOB 정정 업무,
로그인 이메일 교체, 아바타 업로드, 이메일 없는 계정, 미성년 얼굴 등록 정책은 후속 작업입니다.
